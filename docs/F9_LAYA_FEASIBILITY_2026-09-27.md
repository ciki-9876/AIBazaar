# Laya 作为 F9 玩法组件的可行性研究

日期：2026-09-27。状态：**研究完成；接入建议待验证，未决定采用，未实装**。

用户问题：研究 [NandhaKishorM/laya](https://github.com/NandhaKishorM/laya)，判断是否能作为 F9 玩法引擎的一部分。

范围：同时核对 F9 现有三路卡牌战斗、万灯城归物师、自制卡脑暴与电梯生存方向。两条游戏方向独立，下面的候选用途不代表将它们合并。

## 1. 结论与选型建议

**可以试验性引入，推荐定位为规则引擎外侧的语义选择组件。** 它可以把玩家的自然语言、物品记忆或 NPC 情境映射到程序已定义的有限选项。伤害、冷却、资源、库存、地图连通性、奖励、成长与胜负仍由确定性程序计算。

优先级建议：

1. **最值得试：自制旧物的意图理解与机制方向推荐。** 用户写记忆，模型建议保护、治疗、蓄力等方向，玩家定稿；这是现有自制卡提案中一个可独立验证的环节。
2. **有条件试：自然语言与电梯终端互动。** 将表达转为查看状态、询问材料、查看楼层等有限请求；具体数据和文本用真实状态及模板回应。
3. **后续探索：有性格的 NPC 或事件候选排序。** 前提是确实需要理解开放文本，且行为权限、难度预算和已公开敌阵边界都已定义。
4. **不建议交给它：核心战斗裁定、自动平衡、寻路、地图生成或通用技能执行。** 已有程序能精确计算的事情，接入语义模型通常增加成本和误判。

若首版没有自由文本输入，也不需要语义匹配，普通规则与检索可能已经足够；不应只为“游戏有 AI”增加模型。

## 3. 模型到底提供什么

Laya 是文本编码器加决策头，使用非自回归前向计算对给定选项输出分布；不是生成长文本的聊天模型，也不是 LayaAir 游戏引擎。

| 接口 | 返回含义 | 在 F9 可表达什么 |
| --- | --- | --- |
| `choice` | 从请求提供的候选中选一项，附概率分布 | 从几个已批准的玩法方向中推荐一个 |
| `noul` | 某判断成立的概率 | 判断描述是否表达保护同伴的意图 |
| `score` | 有序等级分布及期望等级 | 表达偏好强弱；不能代替实际伤害或强度计算 |

`decide` 把扁平 schema 映射为上述问题，支持枚举、布尔和小范围有界等级；自由字符串、数组、嵌套对象和递归不支持。因此“返回结构化结果”不等于“能生成任意卡牌蓝图”。多个字段各自合法，也不意味着组合后的技能合法。[结构化接口](https://github.com/NandhaKishorM/laya/blob/4066d5d5fbf08b66c6757ddeedbd797bd7655bc0/docs/structured.md)

上游列出的模型分别为英文 421M、多语 322M、专用 typed-decisions 421M。中文应以多语模型为首个评估对象；专用模型的提升来自其业务任务微调，不能直接当作游戏策略能力。多语默认上下文 1024 tokens，可显式扩至 8192；选项说明仍有独立预算，扩大上下文不等于能准确比较整个卡池。[模型卡](https://huggingface.co/convaiinnovations/laya-multilingual)

它不能直接识别玩家上传的图片，也不能自己创作物品名、故事或任意技能文字。完整“上传图案 → 自制卡”流程还需要玩家填写物品资料，或另接视觉/生成模型。图片可以先仅作为玩家自带美术，首个语义实验只处理文字。

## 4. 对宣传指标的具体判断

以下数字都必须保留测试条件：

| 上游证据 | 对 F9 的含义 |
| --- | --- |
| 多语单问题在 T4 上约 32.8 ms | 是指定硬件下的推理测量，不包含 F9 网络、排队、界面和冷启动的完整预算 |
| 上游 4 核 EPYC CPU 测试：多语单问题 p50 193 ms，10 问题 1842 ms | 适合低频交互的可能性值得测；不能承诺低端浏览器或逐帧调用性能 |
| typed-decisions 微调模型准确率 0.766；同表基础英文约 0.361、多语 0.352 | 微调有价值；业务评测结果不能外推到卡牌组合规划 |
| 选项过多时受头部 token 预算限制；上游建议约 20 个以内 | F9 不应一次丢入 50 张完整卡牌，宜先按规则筛成少量候选 |
| 上游不同推理精度/实现的对照存在少量 argmax 不一致 | 不采样也不代表跨设备逐位一致，不能只存 seed 后任意重新推理 |

来源：[上游完整评测](https://github.com/NandhaKishorM/laya/blob/4066d5d5fbf08b66c6757ddeedbd797bd7655bc0/BENCHMARKS.md)。这些任务与 F9 的游戏数据不同，不能当作游戏成功率。

更贴近中文交互的风险来自仓库 `zh_short_commands`：18 条手写回归诊断中，三种 `choice` 表达的准确率分别为 72.22%、77.78%、66.67%；其中一种配置把“太慢了”判为减速，所选项概率约 0.9901。样本很小，而且明确**不是独立留出测试集**；它证明存在高置信度误解，不证明中文整体准确率就是这些数字。[诊断结果](https://github.com/NandhaKishorM/laya/blob/4066d5d5fbf08b66c6757ddeedbd797bd7655bc0/research/benchmarks/zh_short_commands/results/v1/laya-multilingual/report.json)、[样本与标签说明](https://github.com/NandhaKishorM/laya/blob/4066d5d5fbf08b66c6757ddeedbd797bd7655bc0/research/benchmarks/zh_short_commands/data/manifest.json)

“没有文本生成”可以避免生成格式错误和虚构选项，但不能避免选错已存在的选项。置信度也不能直接当成可靠性保证：当前 `choice`/`score` 的 `confidence` 是归一化熵，`answer_confidence` 才是所选项概率；后者仍需在 F9 数据上校准和检验。[置信度源码](https://github.com/NandhaKishorM/laya/blob/4066d5d5fbf08b66c6757ddeedbd797bd7655bc0/laya/common.py#L338)

仓库的贪吃蛇示例也不是模型自主规划能力的可靠评测：模型估计四个方向的危险，程序计算食物距离，并以精确碰撞检查否决致命移动；模型加载失败时仍可进入启发式模式。它展示的“模型建议 + 硬规则约束”适合参考，得分不能归功于模型单独完成。[示例源码](https://github.com/NandhaKishorM/laya/blob/4066d5d5fbf08b66c6757ddeedbd797bd7655bc0/laya-ts/examples/snake.mjs)

## 5. 与 F9 现状的对应关系

| F9 当前事实 | 接入建议与边界 |
| --- | --- |
| `lib/arena-engine.ts` 的 `validateArenaBoard` 校验 UID、成长、占格、重复牌；`simulateArenaDuel` 精确结算 | 所有模型候选仍须经过合法性校验；模型不直接写战斗状态 |
| `lib/arena-challenge.ts` 的 `chooseCounter` 已模拟候选阵容并按结果稳定排序 | 最强反制优先复用模拟搜索；语义模型只在需要人物风格或理解文字策略时增加价值 |
| 引擎按 `cardDef`、`arenaCard`、卡牌编号与具体分支执行效果 | 现有系统不是任意技能 DSL；接模型不会自动得到自由造卡能力 |
| `lib/wandeng-game.ts` 的 `eventOffers`、`itemsFromPool` 使用固定规则/散列生成事件与物品 | 开放语义事件选择属于新玩法提案；当前仅几类事件时，规则实现可能更经济 |
| `previewWandengBattle` 从状态副本构建敌阵；回放保存 battle 输入 | 若未来有模型选敌阵，必须在公开预览前固定并保存，重复预览、开战和回放不能分别再问模型 |
| `lib/survival-world.ts` 的 `generateWorld` 按 seed 与版本生成布局 | 地图仍用程序配方；若用模型选择主题，主题先成为冻结配置，再走原生成器 |
| `lib/survival-gm.ts` 是预设教学检查点工具 | 这里的 GM 不是已存在的 AI 叙事导演，不能把它当作模型接入基础 |
| 现有自制卡文档是脑暴，尚未实现机制编译、预算校准与自由模式 | 可在独立实验中验证语义推荐；正式可玩的自制卡还有单独工程工作 |

## 6. 推荐的第一个玩法实验

**假设 H1：理解玩家自己的物品记忆，再推荐战斗方向，能增强“这是我的东西”的感受。** 尚无试玩证据。

例子：玩家写“奶奶总用这只旧杯子给我留热水”，模型从少量既有方向里推荐治疗、保护或储存后释放。模型不决定故事有多感人就加多少攻击，也不凭“这件东西很重要”增加预算。

建议流程：

```text
一句物品描述 / 记忆 + 玩家已选约束
  → 程序提供少量可用方向
  → Laya 给出选项分布
  → 玩家看到并选择明确的机制预览
  → 程序选用合法蓝图、校验参数与预算
  → 原战斗引擎试炼
  → 冻结蓝图与版本后入局、保存和回放
```

初次实验可以只用现有已实现效果的样板，不必先承诺自由组合。应明确它验证的是“语义对应和选择体验”，不是“无限创作能力”。如果玩家觉得结果只是在换皮，则不能用分类准确率宣称玩法成功。

以后要开放更自由的机制，另行实现受限的技能数据结构、组合校验、预算与模拟验证。规则文本从已批准的可执行结构产生；名称和风味文本不能反向改变能力。

## 7. 确定性、保存与原子执行

以下是根据现有 A-01、A-07、A-08 得出的接入约束建议，不是修改现有设计原则：

1. **保持纯规则核心。** 模型返回方向或候选 ID；规则层校验后，才把一个明确命令交给 reducer/引擎。推理过程中不扣库存、不占配额、不先支付一部分费用。
2. **冻结并记录结果。** 保存模型/权重版本、问题与候选版本、稳定候选顺序、输入摘要、最终选项、蓝图完整内容和规则版本。不能仅存一个在线模型名称或 seed。
3. **区分回放确定性与新局确定性。** 保存 AI 结果可以使同一存档和回放复现，却不能保证另一台设备用同 seed 新开一局时得到相同 AI 结果。要维持后者，优先在制作期生成并固化内容，或让玩家确认的蓝图/命令成为初始输入；若要运行时自动决策，则还需版本化的权威决策记录/固定策略方案，不能暗中放宽现有契约。
4. **稳定的失败路径。** 超时、无模型、低置信度或非法候选时，回到可见的手动方向选择，或使用指定规则兜底。不得悄悄变成随机加成；回放也不重复触发兜底竞态。
5. **处理异步过期。** 给请求绑定状态版本和 ID；返回时若玩家已经切换物品、场景或局面，丢弃旧建议。确认及资源提交必须幂等，不能重复发奖或扣款。
6. **公平与可解释。** NPC 只接收设计允许的信息；已公开敌阵不在玩家整备后暗中重选。展示的是实际采用的规则和行为，不能伪造模型的内心推理作为战斗解释。

第一阶段仅做玩家确认后的语义建议，最容易保留现有确定性合同；自动 NPC 或导演应另作实验。

## 8. 部署可行性

| 路径 | 已核查能力 | 本项目建议 |
| --- | --- | --- |
| Python 常驻服务 | Python SDK 与 `laya-serve` HTTP 接口可用 | 首轮最直接；固定多语 checkpoint，预热一次，在玩法低频节点调用 |
| Node + ONNX | 仓库含 `laya-ts` 0.1.0 和 Node provider | 可减少语言边界，但需导出权重、测试一致性与部署环境 |
| 浏览器 + ONNX | TypeScript provider 中编码器尝试 WebGPU/WASM，决策头使用 WASM | 技术上有路径；尚未验证 F9 打包、设备兼容、加载体积和与 3D 渲染争用 |
| 制作期离线生成 | 可提前执行语义选择并保存普通数据 | 最容易兼容纯离线游戏；玩家实时自由输入的收益有限 |

截至核查时，合集及独立多语权重列表中没有 `encoder.onnx`/`head.onnx`；TypeScript 文档要求先导出。不能认为安装一个 npm 包即可直接浏览器加载现有权重。多语诊断记录的 safetensors 体积约 644 MB；这是权重文件体积，不是 ONNX 下载量，也不是实际内存占用。不能把“小模型”理解为手机网页上的轻量资源。[TypeScript 文档](https://github.com/NandhaKishorM/laya/blob/4066d5d5fbf08b66c6757ddeedbd797bd7655bc0/laya-ts/README.md)、[浏览器 provider](https://github.com/NandhaKishorM/laya/blob/4066d5d5fbf08b66c6757ddeedbd797bd7655bc0/laya-ts/src/providers.ts#L511)

F9 当前为 React/TypeScript、vinext/Vite 工程，存在静态发布脚本与 Wrangler 运行入口；这些不自动提供常驻 PyTorch 或原生 ONNX 进程。服务方式需独立部署/本地伴随进程；如果纯离线首启是硬要求，应优先评估随包模型或离线固化数据。自托管没有按 token 支付给该开源项目的必要，不等于算力、带宽和维护成本为零。

## 9. 最小验证与采用门槛（建议，尚未执行）

先做一个独立的中文语义方向评估，不改现有对局规则，不把下载模型设为游戏启动前提。

| 验证 | 方法 | 怎样决定下一步 |
| --- | --- | --- |
| 是否需要模型 | 对比手动方向、关键词/规则和 Laya；相同输入、相同候选 | 只有当自由表达带来可观察收益时继续 |
| F9 中文理解 | 暂定 200–300 条物品记忆/方向样例，包含否定、隐喻、含混、无关输入与改写 | 先确定标注规则与划分，按物品/故事族留出，避免把近义改写泄漏到训练和测试两侧 |
| 置信度与弃权 | 查看所选项概率、混淆矩阵、覆盖率/错误率；若微调，另留校准集 | 根据验证集设置阈值；不能直接采用 0.8 或把上游校准迁移过来 |
| 选项稳健性 | 相同含义换措辞、换顺序、不同长度；检查截断 | 产品候选保持稳定顺序，同时测排列敏感性；少量候选起步，暂定 3–6 个 |
| 实际开销 | 指定目标 CPU/GPU/浏览器，分别测首次加载、暖启动 p50/p95、内存、总请求时间 | 按玩法等待容忍度决定设备与调用频率，不沿用宣传 33 ms |
| 状态与回放 | 非法候选、断网、超时、重复确认、过期响应、保存加载、重复预览 | 硬要求：不产生非法状态、不重复结算、冻结结果回放一致 |
| 玩家价值 | 少量玩家比较手选方向与文字推荐；观察是否认同、是否修改、是否愿意带入局 | “认得自己的物品、理解代价、候选不同”比平均分类分数更重要 |

如未微调结果不足，再评估领域微调；“支持微调”不是必须投入训练的理由。若规则基线已足够，保留规则即可。若模型只有在自动改动数值、读取隐藏信息或破坏固定预览后才能体现优势，则本接入方向不符合当前 F9 目标。

## 10. 本轮产物与未决问题

产物仅为本报告、设计研究记录与索引链接。没有改动玩法、数据模型、依赖或部署，也没有将推荐登记为已接受 ADR。

后续决策仍需回答：优先服务万灯城还是电梯？玩家是否需要离线首启？目标设备是什么？语义推荐相比直接手选有没有体验收益？这些问题不妨碍本轮可行性判断，但会决定原型部署方式和是否值得投入。

测试状态：本轮是来源与代码静态核查，没有运行 `npm test`、`npm run lint` 或构建；没有可报告的 F9 模型实测。主要剩余风险是中文领域泛化、跨后端一致性、首加载成本、早期项目维护，以及玩法价值尚未验证。
