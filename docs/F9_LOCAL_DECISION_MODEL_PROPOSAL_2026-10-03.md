# F9：Laya 与本地专用决策模型方案

日期：2026-10-03。状态：调研与方案，未选择模型、未下载权重、未训练或接入。用户已明确最终同时支持 Windows 客户端与浏览器；两端的最低硬件、开放交涉范围与是否要求所有功能离线尚未确定。

承接 [Jev 调研](./F9_JEV_FEASIBILITY_2026-10-03.md)、[上一轮 Laya 研究](./F9_LAYA_FEASIBILITY_2026-09-27.md) 与 [模型选手体验要求](./design-log/decisions/ADR-0025-llm-contestants-and-elimination-experience.md)。本文研究电梯竞争者，不将其与卡牌产品耦合。

## 1. 判断

可以制作本地、一次前向计算的 F9 专用决策模型，消除这一层按请求计费与网络等待。**优先路线是以 Laya 等现有开放编码器验证并微调，再视两端性能决定是否蒸馏成更小的结构化策略网络。** 不建议从零预训练一个具备 Jev 通用语言理解与判断能力的模型。

必须分开三个目标：

- **本地快速动作选择**：范围可控，最值得先做。
- **人物关系、资格竞争与跨期策略**：需要记忆、不同目标及长时序训练／评测，不能从动作分类能力自动推出。
- **开放式中文交流、临时提议与新策略生成**：Laya 类选择模型本身不能生成；全本地实现还需要本地生成式模型，或经用户选择收缩为有限交涉系统。

“免费”应具体指运行时不向 API 供应商按调用付费。模型制作、训练、验证、电力、设备、分发和维护仍有成本；部署到我们自己的服务器仍产生持续算力费用。仅把战术层本地化，也不会自动使在线策略／对白的费用归零。

## 2. 本轮核实的 Laya

仓库本轮快照为 `fa9a2a7070b1789912a49ae24603bbfb1a78b001`，提交2026-10-02，版本0.3.24。上轮0.3.20研究保留历史状态。

Laya 是独立开放的非自回归决策模型，接口可选候选、评分或判断是非；仓库与所核对权重页面标注 Apache-2.0。英文与业务专用模型约421M参数，多语模型约322M。发布材料定位是可以领域训练的基础，而非已经具备通用零样本决策能力。[仓库快照](https://github.com/NandhaKishorM/laya/tree/fa9a2a7070b1789912a49ae24603bbfb1a78b001)、[模型卡](https://huggingface.co/convaiinnovations/laya)、[代码许可](https://github.com/NandhaKishorM/laya/blob/fa9a2a7070b1789912a49ae24603bbfb1a78b001/LICENSE)

上游业务评测中基础英文／多语准确率约0.362／0.352，随机基线0.318，领域微调版本报告0.766；这些任务不是游戏。Jev 对照来自第三方发布值，非同一运行环境直接对测，不能据此宣称 Laya 全面胜过 Jev。[评测及限制](https://github.com/NandhaKishorM/laya/blob/fa9a2a7070b1789912a49ae24603bbfb1a78b001/BENCHMARKS.md)

独立预印本复现了约0.767的业务准确率，但发现该特定检查点／任务的置信度偏低及领域外迁移问题；这与基础模型某些任务过度自信可以同时成立。必须在 F9 的校准集和测试集重新评价。[原始研究](https://arxiv.org/abs/2609.33843)

## 3. 本地延迟证据

上游多语模型在 Tesla T4 上单问题约32.8毫秒；Ryzen 9 6900HX 的业务专用模型单问题最佳线程配置约329毫秒；4核 EPYC CPU 上多语单问题约193毫秒，十问题约1842毫秒。它们的请求长度、模型、后端和测量条件不同，不能直接排名，更不能视为普通浏览器保证。[硬件与测量条件](https://github.com/NandhaKishorM/laya/blob/fa9a2a7070b1789912a49ae24603bbfb1a78b001/BENCHMARKS.md)

更贴近“做一个领域模型”的证据是上游收录的浏览器动作微调案例：单张 RTX 4070 Ti SUPER 16GB、无付费 API，原始案例报告多语微调模型每步17–23毫秒。[训练配方与失败经验](https://github.com/NandhaKishorM/laya/blob/fa9a2a7070b1789912a49ae24603bbfb1a78b001/docs/finetune_browser_agent.md)

该项目当前模型卡也明确：满频 GPU 时22–27毫秒，间歇请求下 GPU 降频时75–270毫秒；复杂、未见网站多步任务仅约20–26%成功，不能只引用简单套件的高成功率。它说明领域微调可行，也说明速度提升不能解决多步目标理解。[当前模型卡与结果](https://huggingface.co/cklxx/laya-browser)

F9 尚未实测。要同时测游戏渲染运行时的总决策延迟、帧时间、线程争用、冷启动和内存；空载GPU推理时间不足以决定采用。

## 4. 三种制作路径

| 路径 | 能力与收益 | 主要代价 | 当前建议 |
| --- | --- | --- | --- |
| 直接用原始 Laya | 本地文本到有限选择，可快速做对照 | 没有 F9 训练，领域误判与上下文截断 | 只作实验基线 |
| 在 Laya 上训练 F9 | 保留文本基础，学习房间战术与有限关系决策 | 数据、校准、数百M模型和分发体积 | 首个领域实验候选 |
| 专用小型结构化策略网络 | 只读 F9 特征并给动作打分，有望更轻 | 不自带语言理解，需要自己的训练与泛化验证 | 两端性能的长期候选 |

第三条不必复制 Jev 的未知内部架构。我们可以实现相似的外部用途：角色观察＋当前目标＋合法行动候选→一次前向评分→候选 ID。评分模型必须真正在数据和反馈中学习，不只是包装一份固定权重表。

首个小网络可以尝试约0.5–5M参数的状态／候选编码器和短历史记忆，具体规模由实验决定。仅参数数据按 FP32 计算约2–20MB，FP16约1–10MB；这不含运行库、缓存、工作内存或另用的文本编码器，亦不是已经实现的包体。

若需要任意中文输入，必须保留可处理文字的模型，不能把没有文本编码器的小网络当作聊天理解替代品。规则化物品／地形可以直接给能力字段，减少无意义的文本推理。

## 5. F9 的输入与输出建议

模型只读取选手自身能知道的资料：

- 自身精神、饥渴、装备能力、占格与负重限制。
- 当前可见／可听到的威胁、已知资源点和自己的探索地图。
- 目标、人物倾向、相关承诺、对他人的已观察行为及未确认传闻。
- 最近行动与结果、正在搜索的剩余时间、当前策略是否被新事件阻断。
- 当前可执行候选，各自带目标 ID、路径、距离、遮挡与合法参数。

程序精确算物理事实和行动是否合法；模型判断如何取舍。语义描述可写成“能保持己方射程”“会失去攻击视线”，同时保留精确数值特征；不让模型从坐标猜路线或算伤害。

建议将互相依赖的动作和目标绑定成一项：`移向东侧掩体A并保持与目标B的距离`，而非独立预测目标、方向、敌对状态后盲目拼接。首次 Laya 实验约8–16个具体候选，并检查状态／候选是否截断或同文；过多候选的预算上限会影响区别能力。

人物倾向输入可包括重视承诺、风险偏好、竞争倾向；不能将其写成必然反应脚本。对同样的“合作型角色”，已经背约的对手、正在兑现承诺的对手和陌生人应该引起不同选择。

首版由同一份模型权重服务多个角色，每人独立观察与记忆，避免为每个人重复加载。主题资产变化不改变“高障碍挡视线／低障碍只挡移动”等能力字段，减少每换世界都重训的需要；新增真正机制仍需新测试，不能保证零训练泛化。

## 6. 训练数据怎么来

先建立记录契约，而后收集模型数据。每条记录至少包括：规则／观察／行动 schema 版本、场景与轨迹 ID、角色个人观察、相关目标与记忆、稳定候选及遮罩、行为标签或偏好、标签来源、实际执行结果。全局隐藏状态可以供独立评估器核算后果，不能进入角色或教师的在线观察。

建议分四种来源：

1. **我们标注的高质量情境。** 保存两至多个可接受动作和理由供复核，不把一个任意选择伪装成唯一正确答案。覆盖“资源诱惑但有承诺”“需要水但身后有威胁”等冲突。
2. **程序模拟与反事实结果。** 对候选支付真实时间、运行搜索／战斗／撤退，评价生存、资源、目标和援助后果。对他人的未知状态按角色可能的信念抽样，不能用全知模拟挑出透视动作。
3. **教师模型建议。** 可以选择本地开放生成模型，或在开发时有限使用云端模型。记录其实际选择而非将理由当真相，检查候选是否合法，再由规则结果／人工抽查纠错。云端输出作为训练数据前还需核对该供应商允许的用途，不默认许可蒸馏竞争模型。
4. **真实试玩中的失败状态。** 让学生运行，收集反复绕圈、抢错目标、背约或看见危险仍搜箱的局面，补正确示范再训练。只训练专家顺利轨迹不够。

首个验证集先做约1000–2000条有覆盖的情境及闭环轨迹，再视错误来源扩为约1–5万条；这是工作量起点，不是充分样本保证。数据数量、训练时长和预算需在观察／行动范围固定后才能核算。

训练、校准、最终测试按地图 seed、完整轨迹、情境模板与角色关系分组隔离；相邻帧和同模板改个名字不能分散到训练与测试中刷高分。单独留出未见主题、装备能力组合与玩家策略。

## 7. 模仿、反馈与博弈能力

第一版用监督学习／偏好排序先学具体合法动作，暂不把复杂强化学习当开工前提。再依据闭环失败进行修正，必要时加入短期结果评价、长时序回报与不同对手的自我对抗。

如果标签全由一套“缺水就喝、受伤就跑”的脚本产生，模型只会学到相似策略，不能期待凭参数规模长出复杂欺骗。程序规则可以精确算结果，训练样本必须包含多种有后果的选择和关系冲突。

单一“晋级／击杀奖励最大化”可能让所有角色趋向同一种行为。建议把目标与关系偏好显式条件化，训练不同对手和局面，并评估承诺的实际成本；人物性格不能仅靠最后一句台词区分。

战术蒸馏不能保证继承教师开放式推理。若我们只在制作期使用大模型，发布时完全由小网络＋有限模板运行，应明确这是学习型 AI，不能把它描述成大模型实时与玩家谈判。是否接受这一体验变化，需要后续由用户选择。

## 8. 保留开放博弈且取消运行 API 的路径

可以采用本地快模型＋低频本地生成式模型：

- 快模型处理近期行动、已形成策略下的有限取舍。
- 生成式模型在交涉、关键规则变化和关系事件时制定／修改计划并生成台词，必须拥有实际策略权。
- 游戏系统保存个人记忆、校验交易、执行与判定真实结果。

这样有机会让运行 API 费用归零，但生成模型的模型文件、运行内存及响应时间还需独立选型。3–8B量级可以作为预算候选范围，不是已经确认普通电脑或浏览器能流畅运行的推荐。

若保留云端策略模型，则只是战术层免费；若改用固定对白与交涉菜单，则范围收束更容易，但会缩小用户原先要求的开放博弈。这三种状态要在验收和产品描述中分别记录，不暗中混同。

## 9. 双端部署与性能目标

用户要求同时支持 Windows 客户端与浏览器，不代表批准当前项目迁移或选定桌面壳。

两端先共用观察和动作协议、同一候选语义、模型版本及决策记录。Windows 可试独立本地进程／原生 ONNX 推理；浏览器可试 Worker 中的 ONNX WASM／WebGPU，不阻塞主线程。Laya 上游已有 TypeScript 路径，但须先导出并验证 encoder/head 权重，不是安装 npm 包就完成接入。[TypeScript 部署说明](https://github.com/NandhaKishorM/laya/blob/fa9a2a7070b1789912a49ae24603bbfb1a78b001/laya-ts/README.md)

浏览器的下载／缓存、设备内存、跨源加载及GPU与3D渲染争用都要实测。322M参数仅 FP16 权重理论上约644MB，INT8约322MB；量化能否保留动作质量与跨后端结果需验证，不能仅按文件缩小比例推算速度。

Laya 作为完整文本模型先在桌面验证；为两端的常态动作努力得到足够轻的共同策略模型。不能在浏览器无声切成固定脚本，却声称两端同样具备自由谈判。

建议初测每角色1–2Hz，离屏和无关键变化时降频；三角色在游戏渲染运行中测总负载。小网络可设每批决策P95≤30毫秒的优化目标，Laya按实际设备决定可用频率；二者均未实测。目标不包含瞬间生成复杂谈判，游戏本地30Hz动作继续执行。

训练用强GPU不等于玩家必须有同级GPU；但也不能反过来保证任意低端CPU都满足目标。必须选定最低硬件与浏览器列表后决定发布配置。

## 10. 先做什么与采用标准

建议先实现可替换模型的个人观察、动作候选和记录接口，以一房间、一名竞争者、固定装备与三种人物目标作实验；共同解决追逃、搜刮中断、补给和援助／自利冲突。此顺序是助手建议，本轮未启动开发。

对照原始Laya、领域微调Laya、结构化小策略网络与本地规则基线；先静态快照，再运行多步闭环。胜率之外还看目标达成、承诺一致性、能否被玩家反制、持续行动、对新局面的适应和高置信错误。

在两端分别报告：实际包体、冷启动、P50／P95／P99、总CPU／GPU占用、游戏帧时间、内存、截断、候选遗漏、过期响应和动作错误。界面流畅与模型预测速度要分开统计。

决策输出经校验作为外部输入，固定 tick 提交并保存，回放不重新推理。权重／模型、观察和动作 schema 固定版本；跨设备浮点或量化差异不因不采样而自动消失。保留 UID、原子资源、现有RNG、支持的存档键与产品隔离；不将本地模型运行引入纯规则模块或卡牌产品。

若Laya短战术有效但太重，才推进小模型蒸馏；若教师与数据本身不理解目标，先改数据和任务表示。若长期博弈未过关，不能用出色战术分类替代原体验要求。
