# 02 · 规则功能开发

这一章讲怎样给对决加一条新规则或新机制。以 v5 的两个真实功能为例：**落幕**（全局机制）和**演出规矩 `DuelTerms`**（单局约束）。

## 1. 先回答四个问题

动代码之前，在 PR 描述或 iteration 记录里写下：

1. **玩家体验**：它让哪种打法更有意思？哪种打法会受害？（落幕：让护盾/治疗这类「只活不打」的流派有了赢法。）
2. **克制关系**：它会不会打破现有的克制环？（见 03 第 3 节）
3. **可读性**：玩家能不能在不读规则书的情况下看懂？界面上用什么提示？
4. **版本**：同样的种子会不会出不同结果？会 → 升 `RULES_VERSION`。

## 2. 落地顺序（八步）

每一步都对应 `throw-duel.ts` 或界面里的一个固定位置。按顺序做，漏掉任何一步都会出 bug。

| # | 改什么 | 落幕的做法 | 演出规矩的做法 |
|---|---|---|---|
| 1 | **常量与类型**：参数写成具名导出常量，配 JSDoc 说明「为什么」 | `CURTAIN_MS`、`CURTAIN_RAMP`、`curtainDamage(tick)` | `DuelTerms`、`EndReason` |
| 2 | **状态**：需要记住的东西加到 `ThrowDuel` / `ThrowFighter`，在 `createThrowDuel` 初始化 | 无需新状态（只由 tick 推出） | `state.terms`，经 `options.terms` 传入 |
| 3 | **预览**：会影响出牌结果的，先进 `previewThrow`，保证预览 = 实际 | 变种「谢幕」在 `context.curtain` 为真时生效 | `termsAllow(terms, cards)` 给预览和按钮用 |
| 4 | **出牌**：在 `launchMutable` 里校验与结算；校验失败**直接返回**，不改任何东西 | — | 违规出牌整手拒绝 |
| 5 | **推进**：持续效果放 `stepThrowDuelInPlace`，注意和现有结算的**先后顺序** | 在持续伤害（剧毒、灼烧）之后结算，走普通伤害通道（护盾可挡） | — |
| 6 | **结束**：只通过 `finish()` 里的 `end()` 出口 | 双方同时倒下 → 平局 | 先判血线和时限，再判 120 秒 |
| 7 | **事件**：写进 `state.events`，表现层据此播放 | 落幕伤害事件 | 结束原因 `endReason` |
| 8 | **界面与文字**：对决界面、规则弹窗、预览提示，文字与代码一致 | 倒计时「N 秒后落幕」、幕布下降、规则弹窗里一条说明 | 「本场规矩」提示；违规时按钮置灰并说明原因 |

规则弹窗的文字在 `throw-table.tsx` 的规则列表里（搜「落幕」可以找到）。

## 3. AI 也要懂新规则

AI 用的是和玩家一样的函数：`recommendCards`（选牌）→ `aiReady`（要不要现在出）→ `launchThrowInPlace`。加了新规则后检查：

- AI 会不会因为新规则卡死（一直不出牌）？
- AI 会不会利用新规则做出明显愚蠢的事？
- 演出规矩只约束玩家，所以 AI 不需要遵守；但**模拟工具**里的代理玩家（`apps/throw/tools/sim-proxy.mjs`）需要遵守，否则模拟胜率是假的。

## 4. 原子性检查

每个会失败的操作，都按这张表自查：

| 操作 | 失败条件 | 失败时必须保持不变 |
|---|---|---|
| 出牌 | 牌不连续、违反规矩、手牌里没有这些 uid | 手牌、冷却、出手计数、事件列表 |
| 整理手牌 | 冷却中 | 手牌顺序、冷却 |
| 放道具 | 越界、重叠、超出 10 格 | 整个布局 |
| 创建对决 | 牌匣超出稀有度上限 | 抛错，不返回半成品 |
| 购买 | 钱不够、已拥有、未上架 | 演出费、拥有列表 |

写测试时，**对失败分支断言「状态完全相等」**（`assert.deepEqual(before, after)`），而不只是断言「没有报错」。

## 5. 测试要求

新规则至少要有：

1. **单元测试**：触发条件的边界（刚好触发 / 刚好不触发）。
2. **原子性测试**：失败分支前后状态相等。
3. **确定性测试**：同一种子跑两次，结果完全一致。
4. **结算顺序测试**：如果和其他机制有交互（比如落幕伤害撞上护盾），单独写一个。
5. **平衡回归**：跑一次矩阵（见 08），把新旧对比写进 iteration 记录。

例子：`throw-terms.test.mjs`（演出规矩 7 个测试）、`throw-enchant.test.mjs`（变种 10 个测试）、`throw-strategy.test.mjs`（克制环机制）。

## 6. 设计记录

- 新机制 = 一条 ADR（`docs/design-log/decisions/ADR-00xx-*.md`，模板在 `templates/DECISION.md`）。
- 调参过程 = 一条 iteration（`docs/design-log/iterations/F9/`），写清楚试过哪些值、为什么选这个。例：落幕试过 45 / 60 / 75 秒起，选了 60。
- 规则变了，更新 `03_CURRENT_DESIGN.md` 对应段落，并链接 ADR。
- 被否掉的方案写在 ADR 的「选项」里，不要删。

## 7. 常见坑

- **只改了预览没改结算**（或反过来）：玩家看到的伤害和实际不一样。所有出牌效果都通过 `itemEffects` / `enchantEffects` 生成，预览和出牌共用。
- **用了真实时间**：`Date.now()`、`performance.now()` 只能出现在表现层。
- **在 `.ts` 规则文件里 import 不带扩展名**：Node 直接跑测试时会 `ERR_MODULE_NOT_FOUND`。规则层运行时 import 一律写 `.ts` 后缀。
- **改了抽牌顺序**：哪怕只是多调用了一次 `rng()`，所有种子的牌序都会变。
